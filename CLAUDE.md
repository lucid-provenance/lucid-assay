# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lucid Assay: a single-binary CI tool (`cli/main.py`, packaged as `lucid`/`lucid-assay`, with `plinth`/`plinth-assay` kept as backwards-compatible aliases from its pre-rebrand name) that turns test/coverage/governance signals from a CI run into a deterministic Release Confidence Score (RCS), assembles that into a signed in-toto attestation (DSSE + Sigstore keyless signing), and provides a standalone admission gate (`cli/verify.py`) that CI can enforce against the signed attestation before allowing a merge/deploy.

## Git workflow

**Always work from a branch — never commit directly to `main`.** Before making any change, create or switch to a feature/topic branch first (`git switch -c <name>` or similar). `main` is the default/protected branch this repo ships from.

## Commands

Environment/execution rules (never bypass):
- **NEVER** run `rm -rf .venv` or create new virtual environments.
- **NEVER** invoke `.venv/bin/*` binaries or a bare `pytest` directly (avoids container/host shebang mismatch).
- **ALWAYS** invoke tools via the active `python3` interpreter (`python3 -m pytest`, `python3 -m pip`, `python3 -m sigstore`).

```bash
# Install
python3 -m pip install -e ".[dev]"

# Full test suite (what CI runs)
python3 -m pytest -v tests/

# Single test file / test / class
python3 -m pytest -v tests/test_scorer.py
python3 -m pytest -v tests/test_scorer.py::RCSScorerTests::test_perfect_run_scores_high

# The RCS edge-case suite can also be run via unittest directly
python3 -m unittest tests.test_scorer -v

# Run the attestation pipeline end-to-end (unsigned; see README.md "Try it"
# for the full flag set)
python3 -m cli.main --junit-xml ... --coverage-report ... --image-ref ... \
  --image-digest ... --head-sha ... --repository org/repo --branch main \
  --skip-perf-budget-check --out /tmp/attestation.unsigned.json

# Verify a signed DSSE envelope against admission policy gates
python3 -m cli.verify build/lucid-assay.dsse.json --min-rcs 65 --disallow-degraded

# Construct a SLSA v1.0 provenance statement from this process's own ambient
# GitHub Actions context (intended to run inside an isolated signer job --
# see cli/provenance.py's module docstring)
python3 -m cli.main provenance --subject-name ghcr.io/org/repo --subject-digest sha256:... \
  --repo-dir . --out /tmp/provenance.unsigned.json
```

There is no configured linter/type-checker in `pyproject.toml` — don't invent one.

## Architecture

`cli/main.py::main()` is the pipeline orchestrator; its numbered comments (`# 1.` … `# 10.`) are the canonical map of the flow: parse JUnit/coverage → compute patch coverage from `git diff base...head` → inspect branch governance (GitHub rulesets) → optionally ingest SARIF → hash evidence artifacts → AST-walk the test suite for assertion integrity → `scorer.score_pipeline()` → detect/parse lockfile dependencies (`# 6b.`) → `builder.build_statement()` → write the unsigned statement → fire-and-forget WORM upload → optional Sigstore signing → gate on `--min-rcs`.

**Dependency detection** (`cli/parsers/lockfiles.py`, wired in at `# 6b.`): `detect_and_parse_dependencies(args.repo_dir)` auto-detects and parses uv.lock/poetry.lock/Pipfile.lock/pip-compile-generated requirements.txt/package-lock.json/pnpm-lock.yaml/yarn.lock (Classic v1 and Berry v2+)/go.sum/Gradle dependency locks (with a build.gradle/build.gradle.kts fallback for the — common — case where `dependencyLocking` was never enabled)/Maven lockfiles into the predicate's top-level `resolved_dependencies` array. `pnpm-lock.yaml` and `yarn.lock` are both parsed with a minimal, purpose-built line scanner each rather than a real YAML library — this module stays stdlib-only by design (see the module's own "Hardened against" docstring for why), and what each needs (`resolution: {integrity: ...}`; `version`/`integrity` or `checksum`) is regular enough to scan directly. Yarn Berry's `checksum: <n>/<128-hex>` field is a raw SHA-512 digest, not SRI. The `build.gradle`/`.kts` fallback only matches literal `<configuration> 'group:artifact:version'` string declarations — map-notation, version catalogs, and interpolation are out of scope, and a dynamic version (`31.+`) or range (`[1.0,2.0)`) is excluded the same way pom.xml's `${...}` placeholder is. A `requirements.txt` fails closed to contributing nothing unless it actually carries `--hash=` lines (real pip-compile output) — a hand-written, unhashed one is never mistaken for a lockfile, since filename alone can't tell them apart (`pkg:` PURL + digest per dependency, deduplicated by URI). Fails closed to `[]` on any missing/unreadable/malformed lockfile — never raises, same contract as every other `parsers/*` module. This is lucid-assay's own predicate field, scoring-independent (never an RCS input) — **do not confuse it with SLSA v1.0 provenance's `buildDefinition.resolvedDependencies`**, which lives on a differently-shaped SLSA-provenance predicate entirely; lucid-assay's own predicate isn't SLSA-provenance-shaped. `cli/verify.py`'s `_dependency_check_resolved`/`_dependency_check_locked` read this field directly for the Dependency Materialization Evidence section (see README.md's "SLSA Source & Build Track checklists" section) — deliberately **not** part of the SLSA Build Level 2/3 checklist itself, since SLSA v1.0's ratified Build Track doesn't define a dependency-materialization level (decoupled from Build L2/L3 in the Rev. 8 restructuring). `_dependency_check_locked` requires at least one *non-source* entry to be a real `pkg:` PURL with a `sha256`/`sha512` digest, not just an unpinned/no-digest entry.

**Module boundary discipline** (see README.md "Why this decomposition" for the full rationale): `parsers/*` and `scorer.py` are pure/side-effect-free by design — they're what the adversarial test suites hammer on. `oidc_signer.py` and the WORM upload are the *only* network-touching code, isolated so the pipeline's self-measured 50ms blocking budget (warned on, not enforced, via `--skip-perf-budget-check`) excludes them deliberately.

**RCS scoring** (`cli/scorer.py`): a weighted rollup (`WEIGHTS`: test health 35%, patch coverage 20%, overall coverage 15%, assertion integrity 10%, governance 15%, static analysis/SARIF 5%) where almost every edge case fails *closed* rather than defaulting neutral — zero tests executed floors to 0, missing patch coverage falls back to overall coverage × 0.70 and flags `degraded: true`, no PR context scores a neutral 50 (not full credit). Every component's `reason` is embedded verbatim in the signed predicate so an auditor never has to reverse-engineer a score. See README.md's scoring table before changing weights or edge-case behavior — and update both `WEIGHTS` and that table together; they've drifted out of sync before.

**Signing** (`cli/oidc_signer.py`): calls Sigstore's `Signer.sign_dsse()` library API directly (`sigstore.sign.SigningContext` + `sigstore.dsse.Statement`), **not** the `sigstore` CLI. This matters: `sigstore sign` always produces a hashedrekord/`messageSignature` bundle (a signature over raw artifact bytes), never a DSSE envelope, no matter what's passed as input — and `cli/verify.py` calls `Verifier.verify_dsse()`, which requires a real DSSE envelope and rejects a hashedrekord one outright ("cannot perform DSSE verification on a bundle without a DSSE envelope"). `sigstore attest` doesn't fit either: it restricts `--predicate-type` to the SLSA provenance enum and derives its subject from a hash of the predicate file, rather than accepting the already-assembled Statement's own subject (a container image digest). `Signer.sign_dsse()` is the public entry point both CLI subcommands delegate to internally — if you're touching signing, use it directly rather than reintroducing a CLI subprocess. Fetches the ambient OIDC token itself (GitHub Actions `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN`, or GitLab `CI_JOB_JWT_V2`) and raises rather than silently falling back to an unsigned artifact. The GitHub Actions token fetch retries a transient failure up to `_OIDC_FETCH_MAX_ATTEMPTS` (3) times with a short capped exponential backoff, each attempt bounded by its own `_OIDC_FETCH_TIMEOUT_SECONDS` (10s) timeout — provably bounded (fixed attempts × fixed timeout + capped backoff), never an unbounded/tight retry loop. The full Sigstore bundle (`Bundle.to_json()`) is embedded verbatim in the DSSE envelope under `_sigstore_bundle` — `cli/verify.py` must load it via `Bundle.from_json()` on that embedded bundle, not by hand-reconstructing bundle fields from scraps (an earlier version did this and could never satisfy `sigstore_models`' schema for `tlogEntries`).

**Verification / admission gate** (`cli/verify.py`): rejects any envelope file over `MAX_ENVELOPE_SIZE` (10MB) via a `stat()` size check *before* opening/reading it (`load_envelope()`), so a hostile or corrupt multi-GB file can't exhaust memory just by being pointed at. When `jsonschema` is installed, the predicate is validated against `schema/lucid-attestation-v1.schema.json` before policy/score evaluation and surfaced as `schema_validation_status` — deliberately a `warnings` entry, not a blocking gate: the predicate schema evolves over time (fields get added after real attestations already exist without them), so a mismatch alone must never fail an otherwise-valid run; `jsonschema` missing, the schema file unavailable, or validation itself raising all degrade to `"skipped"` the same way. Otherwise decodes the DSSE envelope defensively (never raises on malformed input, only reports `violations`), and does best-effort Sigstore identity verification (`--cert-identity`/`--expected-repository`/`--expected-workflow`/`--expected-ref`) distinguishing `verified`/`skipped`/`unavailable`/`failed` — only `failed` (an explicit Sigstore rejection) blocks the gate; `unavailable` (offline, no trust root) is a warning, not a failure. `--dry-run` and a `--dry-run-sign`-produced placeholder signature are both treated as `skipped`, never mistaken for a real signature. `--expected-repository` is checked against *both* the legacy v1 (`GitHubWorkflowRepository`, raw `owner/repo`) and current v2 (`OIDCSourceRepositoryURI`, full `https://github.com/owner/repo`) Fulcio cert extensions via `AnyOf`, since which one a given cert carries depends on the Fulcio/token version that minted it. On a `SigstoreVerificationError`, the expected vs. actual certificate claims (SAN, issuer, repo, ref) are dumped to `sys.stderr` so a mismatch is diagnoseable straight from CI logs.

**`cli/verify.py --format json`** emits a structured verification payload whose `source.level_1`..`level_4` and `slsa.level_1`..`level_3` are exactly `result.source_level1`..`source_level4`/`result.slsa_level1`..`slsa_level3` — the same SLSA Source Track (Levels 1-4) and Build Track (Levels 1-3) checklists `_evaluate_source_checklist`/`_evaluate_slsa_checklists` compute once inside `verify_dsse_attestation()` and the text formatter renders via `_format_track_report`, plus the synthesized `verdict` headline (`_format_verdict_banner`). `_build_verify_json_payload()` reshapes that already-computed result into JSON rather than recomputing its own assessment — `--format json` and the default text output must never disagree about SLSA compliance for the same run. See README.md's "SLSA Source & Build Track checklists" section for what each checklist item verifies (real signals only — DSSE decode, `identity_status == "verified"`, a trusted `runDetails.builder.id` — never a hardcoded `"passed": true`) and how each level formally builds on the one below it. Dependency-materialization evidence (`buildDefinition.resolvedDependencies`-shaped counts, now sourced from lucid-assay's own `predicate.resolved_dependencies` + `predicate.artifact.sbom`) is deliberately **not** one of the Build Level 2/3 checklist items — SLSA v1.0's ratified Build Track doesn't define a dependency-materialization level — and instead renders as its own non-gating `--format json` `dependency_governance.items` / text "Dependency Materialization Evidence" section; see `_extract_dependency_evidence`/`_format_dependency_governance_report`. `--json` (no `-f`) is a deprecated alias for `--format json`, kept for backwards compatibility; it still emits the same payload and warns on stderr.

**SLSA Source Track and Build Level 3** (`cli/verify.py`): `--slsa-envelope PATH` lets `verify` evaluate both tracks from two envelopes at once — `_classify_statements()` sorts the primary envelope and this optional second one by `predicateType` into (assay statement, SLSA statement) regardless of argument order, falling back to the primary for either track when only one envelope is given (the same "evaluate whatever we're given, report missing fields honestly" contract the Build checklist has always had — see `_evaluate_slsa_l1`'s docstring — now shared by the Source checklist too). Source Level 3 (`_source_check_retained_history`) requires `vcs.commit_author.verified_github_account == true` — the commit author's email resolved, via GitHub's commits API, to a *linked, verified* GitHub account (`author.login`), not merely a free-text git author name/email (self-reported, trivially spoofed). Fails closed identically on "not captured", "check unavailable" (no token/API failure), and "ran but unverified" — three distinct reasons, one `[✗]` outcome; don't collapse them into a single generic message, the distinction matters for diagnosing CI runs. Collected by `cli/parsers/commit_author.py::inspect_commit_author()` (same ambient `GITHUB_TOKEN` as branch governance) and wired into the predicate at `cli/builder.py`'s `vcs.commit_author`. Build Level 3's two identity checks (`_slsa_check_control_plane_builder_identity`, `_slsa_check_isolated_provenance_generation`) genuinely pass today — confirmed against real CI runs across every current caller (lucid-assay, lucid-console, lucid-dsse-collector, lucid-attest-service, 2026-09-03): provenance construction moved into `lucid-attest-service`'s isolated `sign-client.yml` job, and `TRUSTED_CONTROL_PLANE_BUILDER_IDS` names that one entry (the original `lucid-attest`/`sign.yml` entry was removed the same day — that repo is now archived). `--require-slsa-build-l3` (off by default in the CLI itself — that default is deliberately unchanged) is the only way Build Level 3's outcome reaches `passed`/exit code. As of 2026-09-03 every current caller's own CI workflow (`lucid-assay`, `lucid-console`, `lucid-dsse-collector`, `lucid-attest-service`) passes it explicitly, confirmed real and green on each after bumping `ASSAY_CLI_SHA` to a commit at/after PR #76 (the dependency-materialization decoupling — without it, Build Level 3 still requires the removed third item, which doesn't reliably pass for every caller). Don't add a fifth caller's CI to this list without the same confirmation: a real green run at the pinned commit, not an assumption that "everyone else passes so this will too."

**Commit-author identity** (`cli/parsers/commit_author.py`): queries GitHub's `GET /repos/{repo}/commits/{sha}` and reports `verified_github_account = (response.author.login is not null)` — the top-level `author` field, populated only when GitHub matches the commit's author email to a verified account email, deliberately never conflated with the nested `commit.author.name`/`email` free-text fields (which this module still records, for diagnostics, but never treats as verification). Mirrors `github_rules.py`'s hardening posture (strict `owner/repo` + hash-shaped-SHA validation before any URL is built, missing-token/401/403/404/transport/malformed-JSON all degrade to `available=False`, never raise) and reuses its `GITHUB_API_BASE`/`DEFAULT_TIMEOUT`/`_REPO_RE`/`_extract_http_error_detail` rather than re-implementing them. Source Level 3 itself still requires no cryptographic commit-signing check (GPG/SSH) — a verified GitHub account is the bar it enforces, per an explicit product decision, not a technical limitation. This module *does* separately extract the commit's `commit.verification` block (`verified`/`reason`, plus a signature-type inferred from the PEM header since GitHub's API exposes no parsed key-ID/fingerprint field) as `commit_signature_verified`/`_reason`/`_type` — a genuinely stronger claim than account-link verification, deliberately kept apart from `verified_github_account` and consumed instead by the Repository & Workstation Governance section below, never by Source Level 3's own semantics. **GitHub-web-flow merge commit walk-back**: GitHub auto-signs *every* merge commit it creates through its own merge API/UI with its own `web-flow` bot key, unconditionally — crediting that as the requested commit's own signature would be a false positive on any push-triggered run after a PR merge (confirmed empirically 2026-09-04: a real GitHub-web merge commit came back `verified: true` via GitHub's key while the PR's actual head commit came back `verified: false, reason: "unsigned"`). `_web_flow_merge_second_parent()`/`_resolve_signature_source()` detect this shape (top-level `committer.login == "web-flow"`, a real unspoofable GitHub user object, plus a >=2-parent merge) and walk back to the merge commit's second parent — the real PR branch tip — evaluating *that* commit's signature instead, bounded to `_MAX_WEB_FLOW_WALK_BACK_HOPS` (5) hops, provably terminating. `commit_signature_source_sha` records which commit the verdict came from (`None` when no walk-back was needed); a failed walk-back reports `commit_signature_verified=None`, never silently crediting the web-flow signature. Known residual gap: squash-merged commits (single-parent, nothing to walk back to) aren't corrected for — doesn't affect this platform's own repos, which all merge via true 2-parent "Merge pull request", confirmed against real API responses. `verified_github_account`/`name`/`email`/`github_login` are untouched by the walk-back — a merge commit's own top-level `author` honestly is the human who merged it.

**Repository & Workstation Governance** (`predicate.repository_governance`, built in `cli/builder.py` from `BranchGovernanceReport`'s new `linear_history_required`/`force_pushes_blocked`/`deletions_blocked` fields — `github_rules.py`'s `_derive_branch_hygiene()` reading real ruleset rule-type strings, `required_linear_history`/`non_fast_forward`/`deletion`, off the same `rules/branches/{branch}` response branch governance already fetches — plus `CommitAuthorReport`'s new `commit_signature_*` fields above): four compensating controls for a solo-maintained repo that structurally can't satisfy SLSA Source Level 4's two-party review, rendered by `cli/verify.py`'s `_extract_repository_governance`/`_repo_gov_check_*`/`_format_repository_governance_report`. Deliberately isolated from both the ratified SLSA Build Track and the still-draft Source Track — this project's own policy assessment, not a claim about either specification, the same separation reasoning the Dependency Materialization Evidence section already established for a different signal. Purely informational like that section and the S2C2F Compliance Matrix (flat control list, no cumulative `Status:` line) with one exception: **`--require-commit-signing`** (off by default) folds just the Cryptographic Commit Signing item into `passed`/exit code — the same off-by-default, opt-in-only shape as `--require-slsa-build-l3`. The other three branch-ruleset-hygiene items have no gate path; don't wire them into `--require-commit-signing` or any other flag without a deliberate, separate decision to do so. All four items fail closed identically to every other branch-governance-derived check when the underlying query itself was unavailable, and render (even a failing/unavailable item) whenever `predicate.repository_governance` is present at all, matching `branch_governance`'s own "always show why, never just disappear" convention — `[]` (section omitted) only when the predicate lacks the block entirely (an attestation predating this field).

**`$GITHUB_STEP_SUMMARY` markdown writer** (`cli/verify.py::_write_github_step_summary`): appends (never overwrites) a markdown rendering of the same unified report to the file at that env var, when set — a no-op (never raises) when the env var is absent or the file can't be written. Shares `_render_track_sections()` with the stderr text renderer so the two can never drift apart.

**SARIF static-analysis ingestion** (`cli/parsers/sarif.py`): normalizes one or more `--sarif` inputs (semgrep, trivy, CodeQL, ...) and cross-references each finding's file/line against the patch's changed lines, falling back to suffix-matching on path components when a SARIF artifact URI is absolute or CI-runner-prefixed and doesn't line up with git's repo-root-relative paths. The scorer weighs a finding newly introduced in the patch far more heavily than a pre-existing baseline one. Aggregating multiple `--sarif` inputs fails closed: any single unreadable/corrupt report taints the whole aggregate (`available=False`), same as a bad token taints the whole branch-governance report.

**Branch governance** (`cli/parsers/github_rules.py`): queries GitHub's rules-for-branch and rulesets REST endpoints to check whether "branch protection" *actually* prevents an unreviewed direct push/merge (PR required, non-zero approvals, no bypass actor, admin-enforced) as opposed to merely appearing to. These endpoints normally require `Administration: Read` repository permission, which the default `GITHUB_TOKEN` can never be granted via a workflow's `permissions:` block (`administration` is not a valid scope there — don't try to add it, it breaks the whole workflow at parse time). `.github/workflows/assay.yml` mints a separate GitHub App installation token for this (`actions/create-github-app-token`, skipped on fork PRs since `secrets.APP_PRIVATE_KEY` isn't available in that context) and passes it via `--github-token`. Any 401/403 from these endpoints fails the whole governance report closed (`available=False`) rather than trusting partial data from a bad/under-scoped token; `_actionable_auth_failure_reason()` leads with GitHub's own error-body message (extracted via `_extract_http_error_detail`) rather than assuming it's a token-scope problem.

**Formerly-live platform-tier constraint, resolved on this repo (2026-09-01)**: `billwonch/iui-govplane` (private, GitHub Free) is where the rules-for-branch 403 was first confirmed empirically — correctly-scoped App token, correct branch name, still 403'd with `"Upgrade to GitHub Pro or make this repository public to enable this feature."` — but that repo no longer exists as a separate private one; it was transferred and renamed to this repo, `lucid-provenance/lucid-assay`, now public (GitHub transparently redirects the old owner/name to this repo's `id`; confirmed via `gh api repos/billwonch/iui-govplane`). `rules/branches/main` now returns real ruleset data, no 403. `REASON_CODE_PLATFORM_UNSUPPORTED_TIER` (`BranchGovernanceReport.reason_code`, flows through to `predicate.branch_governance.reason_code`) is still live, correct code — it still fires for any tenant repo genuinely stuck private+Free — it just no longer applies to this repo's own dogfood runs. **What surfaced instead is exactly the case the Note below already anticipated**: this repo's live ruleset (`enforcement: active`, `bypass_actors: []` — so `admin_enforced=True`, no `branch_governance_bypass_permitted` degradation) sets `required_approving_review_count: 0`. A PR is required and direct pushes are blocked, but nothing requires a human to approve one before merge. `_score_governance()`'s `required_approvals == 0` branch (`cli/scorer.py`) catches this independently of `bypass_permits_unreviewed_change()`, capping that component at 60/100 with reason `"branch protection requires 0 approvals (weak governance control)"` — a real, fixable governance gap, confirmed empirically 2026-09-01, not a platform limitation and not a scoring bug. **Note**: private Pro/Team/Enterprise repos *do* support rulesets, so gating policy on repo visibility alone (e.g. `github.event.repository.private`) is wrong — it would also waive strict enforcement for a private paid-plan repo with exactly this kind of real, fixable governance gap.

**`--disallow-degraded` is `reason_code`-aware, not a flat boolean gate.** `RCSResult.degraded_reasons` (`cli/scorer.py`) records *why* a run is degraded -- one entry per independent trigger (`DEGRADED_REASON_*` constants there; branch-governance's and patch-coverage's entries are namespaced `f"branch_governance:{reason_code}"` / `f"patch_coverage:{reason_code}"` when a `reason_code` is set on their respective result objects, else the generic `DEGRADED_REASON_BRANCH_GOVERNANCE_UNVERIFIED` / `DEGRADED_REASON_PATCH_COVERAGE_UNAVAILABLE`) -- and is embedded as `predicate.release_confidence_score.degraded_reasons`. `cli/verify.py`'s `--disallow-degraded` gate only lets a degraded run pass when `degraded_reasons` is non-empty **and every entry** is a member of its `_ALLOWED_DEGRADED_REASONS` set -- currently `"branch_governance:platform_unsupported_tier"` (GitHub Free-plan rulesets limitation) and `"patch_coverage:no_coverable_lines"` (a docs/config-only diff with no code to have coverage over, e.g. a README-only PR). Anything else (a real governance gap, missing PR context, broken SARIF, or `degraded_reasons` missing/malformed on an older or corrupt attestation) still blocks -- fail-closed by construction, not by omission. If you add a new degradation trigger to `score_pipeline()`, give it its own reason code; don't reuse an existing one, or you'll silently change what `--disallow-degraded` exempts. If a trigger is a genuinely unavoidable, non-gameable state (not just "hard to fix"), add its namespaced string to `_ALLOWED_DEGRADED_REASONS` in `cli/verify.py` deliberately -- it isn't automatic. This same fail-closed principle extends to the `degraded` boolean itself, not just `degraded_reasons`: `VerificationResult.degraded` (`cli/verify.py`) is always a concrete bool, never `None` -- an absent field displays as its schema-declared default (`false`, per `schema/lucid-attestation-v1.schema.json`), but `--disallow-degraded` never trusts that display default as a compliance signal. It tracks a separate `degraded_field_present` bool and blocks when the field was missing or malformed, exactly as it would a confirmed `degraded == true` with no exempted reason -- an unconfirmed state must never be treated the same as a confirmed non-degraded one.

Also: on a `pull_request` event, `github.ref_name` resolves to the synthetic `"<number>/merge"` ref, not a real branch — `assay.yml` resolves `--branch` from `github.event.pull_request.base.ref || github.ref_name` instead. If branch governance starts erroring on a nonsense branch name, check that this resolution didn't regress.

**AST assertion-integrity checker** (`cli/parsers/ast_inspector.py`): per `.continue/rules/lucid-assay.md`, preserve *scoped* AST visitor isolation when touching this — never use `ast.walk()` inside a test function's scope, since that would credit assertions inside dead branches, nested defs/lambdas, or swallowed-exception `try` blocks as if they actually execute. It also recognizes and rejects tautological assertions (`assert True`, `self.assertEqual(x, x)`, etc.) and mock-typo bypasses (`mock.assert_called()`).

**Hardening pattern**: nearly every module in `cli/` opens with a docstring block titled "Hardened against:" enumerating the specific failure modes it defends against (injection, auth failures, malformed input, adversarial pagination, etc.). When editing one of these modules, check its docstring first and preserve every listed guarantee — the adversarial/boundary test files (`tests/test_security_boundaries.py`, `tests/test_verify_boundaries.py`, `tests/test_adversarial_ast.py`) exist specifically to hold the line on these.

**Diagnostics-first convention**: a policy violation or auth failure (Sigstore identity mismatch in `cli/verify.py`, a 401/403 from GitHub in `cli/parsers/github_rules.py`) must fail closed *and* explain exactly what's wrong and how to fix it — expected-vs-actual values, the specific permission/scope needed — not just a bare exception message or status code. Follow this when adding new failure paths in these modules.

**Workflow security posture** (`.github/workflows/assay.yml`): every third-party Action is pinned to a full commit SHA with a `# vX` version comment (never a mutable tag alone); `permissions:` stays least-privilege (only what's actually used — see the branch-governance note above for why `administration` can't live there); and any step needing a secret unavailable to fork PRs (e.g. `secrets.APP_PRIVATE_KEY`) is guarded with an `if:` condition rather than left to fail loudly on every external contributor's PR. Build multi-flag shell args as a bash array (`ARGS=(--flag "$val")` / `"${ARGS[@]}"`), never string-concatenation handed to word-splitting (`ARGS="$ARGS --flag \"$val\""` then `$ARGS` unquoted) — the latter can't actually strip embedded quote characters without `eval`, and this exact mistake broke both the Mint and Verify steps' argument passing here before being fixed. Dependencies install via `uv sync --frozen --extra dev` against the committed `uv.lock` (pinned versions *and* hashes) rather than `uv pip install -e ".[dev]"` — deterministic, no implicit re-resolution that could pull in a since-compromised transitive dependency between runs. `uv.lock` and `pyproject.toml`'s `[project.optional-dependencies].dev` must stay in sync — after editing either, regenerate the lock (`uv lock`, or `python3 -m pip install --user uv` first if `uv` isn't on `PATH`) and commit both together; a stale lock makes `--frozen` silently install the wrong (old) dependency set instead of failing loudly. Every subsequent step invokes the synced environment via `uv run --no-sync <cmd>`, not a bare `python`/`pytest` — the latter would hit the runner's system interpreter, not the locked one.

**Container image** (`Dockerfile`, `.github/workflows/publish-image.yml`): publishes the full CLI as `ghcr.io/lucid-provenance/lucid-assay`, public, tagged by commit SHA only — deliberately no `latest` tag, consistent with this project's own explicit-pinning stance (`--min-rcs`, Sigstore identity pins, ...). Unlike `lucid-attest`'s signer image (which packages a narrow, hand-picked file list since it runs with signing privilege), this image carries no trust-boundary constraint and is the entire CLI, self-contained — see the Lucid roadmap's Milestone #19 vs. #18 framing if touching either. Built via `uv sync --frozen --no-dev`, not `pip install .` — both now install `schema/` correctly (see the packaging note below), but `uv sync` resolves against the hash-pinned `uv.lock` rather than re-resolving fresh against `pyproject.toml`'s loose ranges, the same reproducibility argument the image exists for in the first place. `uv sync` also installs the project *editable* by default, which keeps `cli/` and `schema/` as real sibling directories at the build path rather than copied into `site-packages` — the runtime image stage must copy that whole directory to the identical absolute path, never rename it, since the editable install's path reference is absolute, baked in at sync time. `HOME=/tmp` in the image (not a fixed user's home directory) — any invocation that overrides the container's user via `docker run --user "$(id -u):$(id -g)"` (needed whenever writing to a bind-mounted host directory) runs as an arbitrary UID that can't write under a fixed baked-in user's home; `/tmp` is world-writable regardless of UID. `git` is installed in the runtime stage for real, unlike the signer image — patch coverage and provenance construction run `git diff`/`git log` against whatever repo a tenant mounts in.

**Packaging: `schema/` needs `__init__.py` + `[tool.setuptools.package-data]`.** `pyproject.toml`'s `[tool.setuptools.packages.find] include = ["schema*"]` looks sufficient but isn't on its own — setuptools silently skips a directory with no `__init__.py`, and even a real package needs an explicit `package-data` entry to bundle a non-`.py` file (the schema JSON). Without both, a plain `pip install .` never installs `schema/` at all, and `cli/verify.py`'s `_SCHEMA_PATH` (`Path(__file__).resolve().parent.parent / "schema" / "*.json"`) silently resolves to a path that doesn't exist — not a crash, `schema_validation_status` degrades to `"skipped"` by design (see the Verification note above), but permanently, with zero schema-drift diagnostic value, for that install path. This never touched any actual integrity/admission-gate check (`schema_validation_status` only ever feeds `warnings`, never `violations`) — a diagnostics gap, not a security one — but fix it at the source (`schema/__init__.py` + `package-data`) if it ever regresses, don't just work around it in one consumer's build step. Verify any change here empirically (a real `pip install .` into a throwaway venv, checked against `cli.verify._SCHEMA_PATH`), not by reading the config and assuming it works — that's exactly how this bug went unnoticed.

## Supply Chain Integrity & Attestation Invariants

- **Ground Truth Only:** Never hardcode, mock, or synthesize provenance data, SLSA levels, or attestation payloads in production code (`cli/`). All signals, hashes, check results, and metrics must be dynamically extracted and verified from real build inputs, live runtime environments, or parsed artifacts.
- **Fail-Closed Verification:** If metadata is missing, unverified, or tampered with, evaluation checks must evaluate to `false` or non-compliant. Never default to passing states or fabricate fallback signatures.
- **Test Fixture Isolation:** Mocked payloads and synthetic envelopes are strictly confined to `tests/fixtures/` and unit test suites for boundary testing.
- **Zero-Bypass Policy:** Implementations must reflect genuine pipeline states (e.g., actual Git SHAs, ambient OIDC tokens, deterministic lockfile digests, live static analysis results).
