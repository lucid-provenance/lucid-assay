# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lucid Assay: a single-binary CI tool (`cli/main.py`, packaged as `lucid`/`lucid-assay`, with `plinth`/`plinth-assay` kept as backwards-compatible aliases from its pre-rebrand name) that turns test/coverage/governance signals from a CI run into a deterministic Release Confidence Score (RCS), assembles that into a signed in-toto attestation (DSSE + Sigstore keyless signing), and provides a standalone admission gate (`cli/verify.py`) that CI can enforce against the signed attestation before allowing a merge/deploy.

## Git workflow

**Always work from a branch — never commit directly to `main`.** Before making any change, create or switch to a feature/topic branch first (`git switch -c <name>` or similar). `main` is the default/protected branch this repo ships from.

## Commands

Environment/execution rules (never bypass):
- **NEVER** run `rm -rf .venv` or create new virtual environments.
- **NEVER** invoke `.venv/bin/*` binaries or a bare `pytest` directly (avoids container/host shebang mismatch).
- **ALWAYS** invoke tools via the active `python3` interpreter (`python3 -m pytest`, `python3 -m pip`, `python3 -m sigstore`).

```bash
# Install
python3 -m pip install -e ".[dev]"

# Full test suite (what CI runs)
python3 -m pytest -v tests/

# Single test file / test / class
python3 -m pytest -v tests/test_scorer.py
python3 -m pytest -v tests/test_scorer.py::RCSScorerTests::test_perfect_run_scores_high

# The RCS edge-case suite can also be run via unittest directly
python3 -m unittest tests.test_scorer -v

# Run the attestation pipeline end-to-end (unsigned; see README.md "Try it"
# for the full flag set)
python3 -m cli.main --junit-xml ... --coverage-report ... --image-ref ... \
  --image-digest ... --head-sha ... --repository org/repo --branch main \
  --skip-perf-budget-check --out /tmp/attestation.unsigned.json

# Verify a signed DSSE envelope against admission policy gates
python3 -m cli.verify build/lucid-assay.dsse.json --min-rcs 65 --disallow-degraded

# Construct a SLSA v1.0 provenance statement from this process's own ambient
# GitHub Actions context (intended to run inside an isolated signer job --
# see cli/provenance.py's module docstring)
python3 -m cli.main provenance --subject-name ghcr.io/org/repo --subject-digest sha256:... \
  --repo-dir . --out /tmp/provenance.unsigned.json
```

There is no configured linter/type-checker in `pyproject.toml` — don't invent one.

## Architecture

`cli/main.py::main()` is the pipeline orchestrator; its numbered comments (`# 1.` … `# 10.`) are the canonical map of the flow: parse JUnit/coverage → compute patch coverage from `git diff base...head` → inspect branch governance (GitHub rulesets) → optionally ingest SARIF → hash evidence artifacts → AST-walk the test suite for assertion integrity → `scorer.score_pipeline()` → detect/parse lockfile dependencies (`# 6b.`) → `builder.build_statement()` → write the unsigned statement → fire-and-forget WORM upload → optional Sigstore signing → gate on `--min-rcs`.

**Dependency detection** (`cli/parsers/lockfiles.py`, wired in at `# 6b.`): `detect_and_parse_dependencies(args.repo_dir)` auto-detects and parses uv.lock/poetry.lock/Pipfile.lock/pip-compile-generated requirements.txt/package-lock.json/pnpm-lock.yaml/yarn.lock (Classic v1 and Berry v2+)/go.sum/Gradle dependency locks (with a build.gradle/build.gradle.kts fallback for the — common — case where `dependencyLocking` was never enabled)/Maven lockfiles into the predicate's top-level `resolved_dependencies` array. `pnpm-lock.yaml` and `yarn.lock` are both parsed with a minimal, purpose-built line scanner each rather than a real YAML library — this module stays stdlib-only by design (see the module's own "Hardened against" docstring for why), and what each needs (`resolution: {integrity: ...}`; `version`/`integrity` or `checksum`) is regular enough to scan directly. Yarn Berry's `checksum: <n>/<128-hex>` field is a raw SHA-512 digest, not SRI. The `build.gradle`/`.kts` fallback only matches literal `<configuration> 'group:artifact:version'` string declarations — map-notation, version catalogs, and interpolation are out of scope, and a dynamic version (`31.+`) or range (`[1.0,2.0)`) is excluded the same way pom.xml's `${...}` placeholder is. A `requirements.txt` fails closed to contributing nothing unless it actually carries `--hash=` lines (real pip-compile output) — a hand-written, unhashed one is never mistaken for a lockfile, since filename alone can't tell them apart (`pkg:` PURL + digest per dependency, deduplicated by URI). Fails closed to `[]` on any missing/unreadable/malformed lockfile — never raises, same contract as every other `parsers/*` module. This is lucid-assay's own predicate field, scoring-independent (never an RCS input) — **do not confuse it with SLSA v1.0 provenance's `buildDefinition.resolvedDependencies`**, which lives on a differently-shaped SLSA-provenance predicate entirely; lucid-assay's own predicate isn't SLSA-provenance-shaped. `cli/verify.py`'s `_dependency_check_resolved`/`_dependency_check_locked` read this field directly for the Dependency Materialization Evidence section (see README.md's "SLSA Source & Build Track checklists" section) — deliberately **not** part of the SLSA Build Level 2/3 checklist itself, since SLSA v1.0's ratified Build Track doesn't define a dependency-materialization level (decoupled from Build L2/L3 in the Rev. 8 restructuring). `_dependency_check_locked` requires at least one *non-source* entry to be a real `pkg:` PURL with a `sha256`/`sha512` digest, not just an unpinned/no-digest entry.

**Module boundary discipline** (see README.md "Why this decomposition" for the full rationale): `parsers/*` and `scorer.py` are pure/side-effect-free by design — they're what the adversarial test suites hammer on. `oidc_signer.py` and the WORM upload are the *only* network-touching code, isolated so the pipeline's self-measured 50ms blocking budget (warned on, not enforced, via `--skip-perf-budget-check`) excludes them deliberately.

**RCS scoring** (`cli/scorer.py`): a weighted rollup (`WEIGHTS`: test health 30%, patch coverage 20%, overall coverage 15%, governance 20%, static analysis/SARIF 15%) where almost every edge case fails *closed* rather than defaulting neutral — zero tests executed floors to 0, missing patch coverage falls back to overall coverage × 0.70 and flags `degraded: true`, no PR context scores a neutral 50 (not full credit). Every component's `reason` is embedded verbatim in the signed predicate so an auditor never has to reverse-engineer a score. See README.md's scoring table before changing weights or edge-case behavior — and update both `WEIGHTS` and that table together; they've drifted out of sync before. `assertion_integrity` (the former sixth bucket, an AST-density proxy) is retired — see the Mutation testing paragraph below for what replaced it and why.

**Mutation testing multiplier, not a scored bucket** (`cli/mutation.py`, fixed 2026-09-11): coverage and assertion counts can both be satisfied by a test that executes a line without ever verifying its behavior — mutation testing is the real check on whether that's happening, so it discounts `WEIGHTS`' test_health/patch_coverage/overall_coverage subtotal via `release_confidence_score.mutation_multiplier` (1.0 ≥80% kill rate / 0.85 for 60–79% / 0.50 below 60%) rather than adding its own additive weighted share — this is a deliberate design call (Bill's own framing: "the mutation score should directly discount the credit awarded to coverage and test health," not just add another bucket alongside them). Diff-scoped to exactly the `*.py` files `patch_coverage.compute_patch_modified_lines()` says changed (the same already-hardened diff `parsers/sarif.py` reuses — no second git invocation), via mutmut (new `mutmut>=3.7.0,<4.0.0` dev dependency) — confirmed against mutmut's real 3.7.0 source, not assumed from its docs, that it has no built-in diff-filtering of its own, so file-level scoping is done with a `mutmut run "<dotted.module>.*"` wildcard per changed file (mutant generation still covers whatever `source_paths` *that target repo's own* `pyproject.toml`/`setup.cfg` configures for mutmut every run, cheap and test-free; only the wildcard-matched mutants are actually *tested*, which is what keeps this bounded). **Deliberately not gated to lucid-assay's own `cli/` layout** — lucid-assay is a generic tool other repos run against their own checkout (lucid-console, lucid-dsse-collector, lucid-attest-service all invoke it in their own CI), so a hardcoded directory-name filter would silently do nothing for every one of them; this was a real bug caught and fixed the same day this feature landed (2026-09-11), before it was ever pushed. Test files are excluded from scope via a naming-convention heuristic (`test_*.py`/`*_test.py`, or under a `tests`/`test` directory), not a directory allowlist. lucid-assay's own dogfooding config lives in *its own* `pyproject.toml`'s `[tool.mutmut]` (`source_paths=["cli","scripts","schema"]`, `only_mutate=["cli/*"]` — `scripts/`+`schema/` are copied-not-mutated siblings mutmut's own baseline test collection needs importable from inside its `mutants/` working copy). The `mutants/` cache is deleted and rebuilt from scratch before every invocation — `mutmut export-cicd-stats` aggregates across its *entire* cache directory, not just what the current invocation tested, confirmed empirically, so a stale result from a prior, differently-scoped run could otherwise leak into this run's `mutation_score`. Two operational safeguards, both full-credit (`multiplier=1.0`), not fail-closed penalties, since neither is a control anyone dodged: the **zero-mutant exemption** (`mutation_testing:no_coverable_lines`, allowlisted in `_ALLOWED_DEGRADED_REASONS` the same as `patch_coverage:no_coverable_lines`) for a diff that changed `*.py` but mutmut generated zero mutants for it (comment/docstring/type-annotation-only — confirmed empirically that mutmut's own `run <wildcard>` otherwise raises an uncaught `AssertionError` on a zero-match wildcard, detected via that specific stderr marker rather than any non-zero exit, which would also fire on a genuine crash), and the **minimum statistical floor** (`MUTATION_MIN_SAMPLE_SIZE_DEFAULT = 3` mutants actually tested — `killed+survived+timeout`, never mutmut's own `total` count, which includes never-tested mutants) for a sample too small to trust (`grade="insufficient_sample"`). Skipping mutation testing (`--skip-mutation-testing`) or a genuine tool failure/timeout is **not** full credit, unlike those two — both apply the same 0.85 multiplier as the weak tier, fail-closed by design, so opting out is never the cheap way to dodge the control meant to stop exactly that gaming. Top surviving-mutant detail (`predicate.mutation_testing.top_surviving_mutants`, ≤5) carries mutmut's own real unified diff verbatim — deliberately never a synthesized mutation-operator taxonomy label mutmut doesn't itself expose, per this file's Ground-Truth-Only invariant. The AST engine's tautology/mock-typo/density diagnostics that used to feed the retired `assertion_integrity` bucket keep running unchanged, now surfacing purely as the informational `predicate.assertion_density` block (`cli/verify.py`'s report renderer, non-gating) rather than a scored component. New opt-in gate: `--require-mutation-score` (`cli/verify.py`, off by default, same shape as `--require-slsa-build-l3`/`--require-commit-signing`) folds only `grade=="failed"` into `passed`/exit code — narrower than `--disallow-degraded`, which the weak/degraded tier already blocks by default regardless (its reason code isn't allowlisted). **Existing informational-only report sections with no gate flag today** (S2C2F Compliance Matrix, the three non-commit-signing Repository Governance branch-hygiene items, Dependency Materialization Evidence, SLSA Source Track L1/L2/L4, SLSA Build Track L1/L2) were inventoried during this work but deliberately left unflagged — a separate, later scope decision per item, not bundled here; `schema_validation_status` is the one section that must *never* get a gate flag (CLAUDE.md's own pre-existing invariant).

**Multi-language mutation testing, same day (2026-09-11)**: `cli/mutation.py` became the `cli/mutation/` package — a dispatcher (`__init__.py`) mirroring `parsers/ast/`'s own registry pattern, `common.py` (shared result shapes + the single `grade_from_score`/`discount_reason` used regardless of which language(s) ran), and one runner module per language: `python_runner.py` (mutmut, unchanged behavior, moved verbatim), `tsjs_runner.py` (new: [Stryker](https://stryker-mutator.io/)), `java_runner.py` (new: [PIT](https://pitest.org/), Maven only). `cli/scorer.py` needed **zero changes** — it already only consumes whatever `MutationTestReport` it's handed. A diff touching more than one language sums every language's real killed/survived/timeout into one combined total before grading once — no per-language weighting, no "worst grade wins"; `predicate.mutation_testing.by_language` (mirrors `assertion_density.languages`'s own per-language precedent) keeps each language's own breakdown visible. Every claim below was verified against a real toolchain this session (portable Node/JDK/Maven downloaded into the scratchpad, since neither was on this sandbox's PATH), not assumed from docs — two real findings only empirical verification caught: **PIT's `scmMutationCoverage` goal doesn't exist in open-source PIT** (it's gated behind PIT's commercial ArcMutate add-on; real scoping instead uses `-DtargetClasses=<fqcn>`, confirmed as a real per-invocation Maven CLI override), and **PIT's XML report's `status` is an attribute of `<mutation>`, not a child element** (`mutation.get("status")`, not `mutation.findtext("status")` — the first draft used the wrong accessor and a real fixture-based test caught it returning 0 killed instead of 1 before this ever shipped). Also confirmed and fixed: Stryker's `.stryker-tmp/` sandbox directory survives in the *target* repo after a run unless `--cleanTempDir always` is passed explicitly (a crashed run leaves it behind regardless) — `tsjs_runner.py` deletes it defensively both before and after every invocation, since leaving it behind would dirty the exact working tree this pipeline's own git-diff-based provenance hashing reads next. **Deliberate scope decision**: the published container image (`Dockerfile`) stays Python-only — Node/JDK/Maven are not bundled in; a missing binary degrades to `unavailable` (fail-closed, not a crash), and most real CI runners already carry all three for a genuinely polyglot repo, so bundling them into every pure-Python pull's image would roughly 5-10x its size for a capability most pulls never use. Go (the AST engine's fourth language) is explicitly out of scope for this pass — Bill's own list didn't include it.

**`python_runner.py` invokes mutmut via `uv run --with`, not `sys.executable`, fixed 2026-09-12** — the first real mutation-testing run against any caller repo other than lucid-assay itself (lucid-dsse-collector, PR #59) surfaced a genuine, previously-unhit design gap: `sys.executable` (the interpreter running `cli.main`) is `_assay/.venv`'s own isolated Python in CI, pinned to lucid-assay's own dependency set (mutmut, pytest, sigstore, ...) — never the calling repo's own runtime/test dependencies (fastapi, sqlalchemy, whatever). Mutmut's internal pytest run then fails to even *collect* the target's test files (`ModuleNotFoundError: No module named 'fastapi'`), and since pytest prints a collection error to stdout, not stderr, the failure surfaced as a blank `mutmut run failed (exit 1): )` — a second, independent diagnostics bug (`_run_scoped`'s reason string read only `.stderr`) that made this far harder to see than it needed to be; fixed alongside (falls back to stdout only when stderr is empty). This went uncaught by this feature's own landing measurement (the "100% kill rate, re-measured against PR #55's diff" claim in `assay.yml`'s `ASSAY_CLI_SHA` comment) because that measurement ran locally, not through a genuinely isolated `_assay/.venv`-equivalent. Real fix: `_run_mutmut()` now shells out through `uv run --with mutmut==<pinned version, read dynamically via importlib.metadata.version("mutmut") rather than hardcoded a second time> --no-sync python -m mutmut <args>` — `--no-sync` reuses the target repo's own already-synced `.venv` exactly as its CI left it (every current caller's own workflow runs `uv sync --frozen --extra dev` earlier in the same job, confirmed), never triggering a surprise re-resolve of that repo's own lockfile; `--with` layers mutmut on top as an ephemeral, uv-resolved addition, never written into the target's own `pyproject.toml`/`uv.lock` (confirmed via a clean `git status` after a real invocation). Relies on `cwd=cwd` for uv's own cwd-based project discovery — the same convention every caller's CI already uses elsewhere (`cd _assay && uv run --no-sync ...`), not an explicit `--project` flag. **New requirement this creates**: a calling repo must itself be a real uv project (a `pyproject.toml` uv can resolve `--with` against) with its own `[tool.mutmut]` `source_paths` configured (see lucid-dsse-collector's own CLAUDE.md for that half of this same incident) — `lucid-attest-service` has neither yet (no `pyproject.toml` at all) and will need both before its own `ASSAY_CLI_SHA` is ever repinned past this fix. Verified via a real, unmocked `run_mutation_testing()` call against lucid-dsse-collector's actual repo (not a unit-test mock) before this was considered fixed: `available=True, grade="passed", killed=6/6`. **This fix's own real CI run then correctly turned mutation testing on for lucid-assay's own dogfooding of this diff** — and found a real, if incidental, gap: function-scoped mutation testing tests the *whole* touched function, not just changed lines, so `_run_mutmut`'s and `_run_scoped`'s own large pre-existing bodies got mutation-tested at this granularity for the first time, surfacing 61 genuine survivors (66% kill rate, `degraded`) that predated this specific edit but happened to live inside the two functions it touched. Closed the same day with `tests/test_mutation.py`'s new `PythonRunnerRunDirectFieldTests` class — calls `python_runner.run()` directly rather than through the lossy `run_mutation_testing()` combining layer, so every `LanguageRunResult` field (`language`/`status`/`reason`/`killed`/`survived`/`timeout`/`total_generated`/`scoped_files`/`surviving_mutants`) can be asserted exactly, closing the same dict-key/kwarg-to-None/string-case survivor shapes this file's earlier incidents already catalog. Re-measured at 98% (175/178 killed) — the residual 3 are genuine equivalent mutants, documented in `python_runner.py`'s own docstring rather than chased (a stderr-fallback string that can never actually be observed, and two encoding-name variants that behave identically to `"utf-8"` on any real UTF-8 locale).

**A changed `*.py` file outside a target repo's own `source_paths` crashes mutation testing entirely, fixed 2026-09-13** — found via `lucid-dsse-collector`'s own PR #62 (a real digest-pinning CI/CD fix, unrelated to mutation testing), the first diff any caller ever landed that added a `.py` file (`scripts/submit_deployment_verification.py`) sitting outside its own `[tool.mutmut] source_paths = ["app"]`. This is a *different* failure shape than the already-handled "wildcard matches zero of many generated mutants" case (`_NO_MATCH_MARKER`, a clean `AssertionError` on stderr): `_scoped_only_mutate()` narrows `only_mutate` to the diff's own files regardless of whether they're under `source_paths` at all, and when none are, mutmut's generation phase produces **zero mutated files at all** and exits 1 with an entirely different, undocumented message on **stdout**, not stderr ("Stopping early, because we could not find any test case for any mutant") — confirmed empirically by reproducing the exact real subprocess call, not assumed from the truncated CI log (which itself only showed spinner-animation frames, `[:300]`-truncated before the real message). Invisible to the existing stderr-only marker check, this surfaced as a confusing generic `unavailable` crash instead of the same zero-coverable-lines exemption a comment-only diff already gets. Fixed by checking containment *before* ever invoking mutmut: new `_read_source_paths()` reads the target's own real `source_paths` off its `pyproject.toml` (same restricted single-line-assignment scan `_is_only_mutate_assignment` already uses for `only_mutate`), and `run()` drops any changed file outside it — exempting the whole run only when *every* changed file is out of scope, never discarding an in-scope file alongside an out-of-scope one in the same diff (confirmed via a real mixed-diff test). Falls back to attempting mutmut regardless when `source_paths` can't be confidently read — never guesses a scope mutmut itself didn't declare. New tests close both the helper functions directly (`IsSourcePathsAssignmentTests`/`ReadSourcePathsTests`/`IsWithinSourcePathsTests`) and `run()`'s own new short-circuit end-to-end (`RunSkipsFilesOutsideSourcePathsTests`, including asserting `_run_mutmut` is never even called for an all-out-of-scope diff). Re-measured at 97% (116/119 killed) — the residual 3 are two more instances of the same encoding-equivalence class above plus a `.lstrip()`/`.rstrip()` swap `json.loads()`'s own whitespace tolerance makes unobservable either way, all documented in `python_runner.py`'s docstring.

**A genuine mutmut failure's own error message was silently displaced by a harmless `uv` warning, fixed 2026-09-13** — found via a real `lucid-dsse-collector` PR (#65) whose mutation-testing step failed with a reason string showing only `warning: VIRTUAL_ENV=_assay/.venv does not match the project environment path .venv and will be ignored; use --active to target the active environment instead` followed by an unrelated `Installed 19 packages in 17ms`, truncated at 300 chars with no trace of whatever actually went wrong. Root cause: `cli.main` always runs inside `_assay/.venv`, so `VIRTUAL_ENV` is already set to that path in the ambient environment `_run_mutmut()`'s subprocess inherits; `uv run --no-sync` correctly resolves the *target* repo's own project-relative `.venv` via `cwd` regardless, but also compares that resolution against the inherited `VIRTUAL_ENV`, finds a mismatch, and prints the warning above to **stderr** — functionally harmless (uv already does the right thing; the warning says so itself), but `_run_scoped`'s `error_detail = (run_proc.stderr or "").strip() or (run_proc.stdout or "").strip()` prefers non-empty stderr unconditionally, so once uv started emitting this warning, a real mutmut failure's own message (typically on stdout) was never seen at all. This is the same "stderr preferred over stdout" fallback that was already fixed once, for a different reason, when the `uv run --with` invocation itself landed (2026-09-12, see above) — that fix handled *empty* stderr correctly, but never anticipated `uv` itself adding a new, unrelated, always-present noise source to stderr on every single invocation. Fixed at the actual source, not by patching the fallback heuristic: `_run_mutmut()` now explicitly strips `VIRTUAL_ENV` from the subprocess's own environment (`env = os.environ.copy(); env.pop("VIRTUAL_ENV", None)`) before invoking `uv run` — this doesn't change which environment uv resolves (it was already correctly cwd-relative, ignoring the mismatched value), it just removes the input that made uv think a mismatch was worth warning about, so stderr goes back to being genuinely empty on a clean run and a real failure's stdout message is no longer masked. New tests (`RunMutmutSubprocessInvocationTests`) lock in both that `VIRTUAL_ENV` is dropped and that every *other* environment variable (e.g. `PATH`) is preserved untouched. Lesson for future changes to this invocation: any new wrapper layer (`uv`, or a future replacement) that writes its own diagnostic chatter to stderr is a latent risk to this exact fallback heuristic — check what it emits under a mismatched/unusual ambient environment before trusting that stderr will stay empty on success.

**That lesson understated the actual scope of the problem, confirmed the very next real run, same day.** Once the `VIRTUAL_ENV` fix above shipped, `lucid-dsse-collector` PR #65's mutation-testing step failed again with a reason string reading only `Installed 19 packages in 24ms` — no warning this time, just `uv`'s own completely routine install-progress line, with the real mutmut error nowhere to be seen. Confirmed by direct reproduction (not assumed): `uv run --with <pkg> --no-sync <cmd>` writes `Installed N packages in Nms` to **stderr** on *every* invocation, success or failure, entirely independent of the wrapped command's own outcome — and the wrapped command's own stderr writes merge into that same stream (its stdout stays fully separate). This means the "prefer non-empty stderr" heuristic was never actually fixed by stripping one specific noise source (`VIRTUAL_ENV`) — `uv run --with` guarantees stderr is *never* truly empty, so a real stdout-based failure (a pytest collection error, the exact shape that originally motivated the empty-stderr fallback in the first place) was still being silently discarded, just by a different, even more mundane line each time. Fixed for real this time by changing the combining logic itself rather than chasing individual noise strings: `_run_scoped` now concatenates both streams (`"stdout: {stdout} | stderr: {stderr}"`) whenever both are non-empty, falling back to whichever one is non-empty when only one is, so a real error is never dropped regardless of which stream it lands on — `uv`'s own noise riding alongside it in the combined string is a minor readability cost, not a suppression bug. Updated the two tests that had encoded the disproven "stderr always wins" assumption as their own expected behavior (`RunScopedGeneralFailureTests`/`MutationTestingReportTests`) to assert the new combined-stream contract instead, and added dedicated truncation coverage for the combined-string case. Full 1529-test suite green. General lesson, sharper than the one above: don't fix a "wrong stream chosen" bug by removing one specific source of noise from the "winning" stream — fix the selection logic itself, since another wrapper-emitted noise source is exactly as likely to recur.

**Independent code review (Gemini, via Continue), same day, six real bugs confirmed and fixed.** Bill's own framing going in: "It all feels very fragile to me" — asked for a genuinely independent second opinion on `cli/mutation/` given its incident history above, then expanded the review to the rest of `cli/`. Every finding was verified against the real code (and in two cases, by direct local reproduction) before being accepted or rejected — one finding (a claimed SARIF path-traversal vulnerability) did not survive that verification and was **not** fixed; see its own entry below for why. The six real ones:

  - **`cli/mutation/python_runner.py` — `_read_source_paths()`'s TOML-array parser rejected several TOML-legal forms.** `json.loads()` (stricter than TOML) silently failed closed on a single-quoted array (`source_paths = ['app']`), a trailing comma (`["app",]`), or a genuinely multi-line array — all three fell back to "attempt mutmut regardless," reopening the exact PR #98 crash for any repo formatting its config that way. `tomllib` (stdlib since Python 3.11) was the obvious clean fix but **deliberately not used** — this package's own `pyproject.toml` still claims `requires-python = ">=3.10"` (unverified/unexercised in CI, which only ever runs 3.13, but not something to unilaterally narrow as a side effect of this fix). Replaced with a small, narrow hand-rolled parser (`_parse_toml_string_array`) handling both quote styles, trailing commas, and multi-line joining (`_find_source_paths_value_text`), staying stdlib-only and 3.10-compatible. Defense-in-depth added alongside: `_STOPPING_EARLY_MARKER` (mutmut's own "generated zero mutants at all" stdout message) is now checked the same way `_NO_MATCH_MARKER` (stderr) already was, so even a source_paths shape this narrow parser doesn't understand converts the resulting crash into the correct full-credit exemption rather than an `unavailable` penalty.

A real multi-module Maven reactor — the norm for anything non-trivial — commonly declares the plugin in a child module's own `pom.xml` and writes that module's report under its own `target/`, not the aggregator root's; this runner silently reported `not_configured` or failed closed on every single invocation against one. Any one module's report failing to parse still fails the whole run closed, never silently reporting on only the modules that happened to succeed.
  - **`cli/mutation/tsjs_runner.py` — fails *open*, the most severe of the six.** When Stryker's default JSON report path (`reports/mutation/mutation.json`) couldn't be read and the process exited 0, the code assumed "nothing to mutate" and granted full credit. Confirmed (Stryker's own docs, and a caller-behavior check) that there is **no CLI flag** to override `jsonReporter.fileName` — it's config-file-only — so a target repo customizing that setting would have real, generated, possibly-surviving mutants silently scored as if nothing needed mutating at all. This is exactly the failure shape this project's own Ground-Truth-Only/fail-closed invariants exist to prevent. More importantly, the dangerous branch itself is gone: a report that still can't be found or read is now always `unavailable` (fail-closed), never full credit — a genuine "nothing mutable" result only ever comes from reading a real report and finding it empty (already handled correctly, separately, by `_collect_from_report`), never from failing to find one.
  - **`cli/patch_coverage.py` — `_parse_diff_output()` misread an added line as a file-header line.** In `git diff --unified=0` output, a real added source line whose own content starts with `++ ` (a plausible C/C++/Java prefix-increment style, e.g. `++ i;`) becomes `+++ i;` once diffed — indistinguishable from a real `+++ b/<path>` header by prefix alone, and mistaking it for one reset `current_file` to `None`, silently dropping every subsequent added line in that hunk. Fixed by tracking hunk state (`in_hunk`): a `+++ ` line is only ever treated as a real header when not currently inside a hunk body, re-armed by git's own always-present, effectively-unambiguous `diff --git a/<path> b/<path>` file-section marker rather than by `---`/`+++` themselves (which are exactly the lines this ambiguity is about). Verified against a *real* git repo, not a hand-written diff string — real `git diff` output is what this must actually parse correctly.
  - **`cli/parsers/sarif.py` — two independent fixes.** (1) `_extract_int_metric()` rejected a comma-formatted SonarQube metric value (`"1,000"`) outright — `float()` raised, silently dropping the metric. Fixed by stripping thousands-separator commas from string values (never touching an already-numeric value) before coercion. (2) `_normalize_sarif_path()`'s traversal-stripping loop only ever handled forward-slash-separated payloads correctly (confirmed by direct trace-through against both of the review's own example payloads, `file:///etc/shadow` and a `../../../../` traversal — both were already neutralized correctly, contrary to what the review claimed) — a genuine, narrower gap found *while* verifying that claim: a Windows-style backslash payload (`..\..\etc\shadow`) survived with its `..` segments intact, since `os.sep` is `/` on the POSIX runners this always runs on. Fixed by normalizing backslashes to forward slashes before the rest of the existing logic runs. Low real-world impact either way — this value is only ever used as a dict-lookup key against `patch_modified_lines`, never to open a file — but fixed for correctness regardless.
  - **`cli/parsers/github_rules.py` — `_parse_link_header()` could silently lose a real pagination link.** `.split(";")` over the *whole* segment (URL included) would fragment a URL containing a literal `;` (legal in a URI, though GitHub's own pagination URLs never use one today — a GitHub Enterprise Server or an intermediary proxy isn't guaranteed to match that) — the truncated segment then failed its own validity check and was silently skipped, meaning a later page (potentially containing a real branch-governance bypass actor) would never be fetched, with nothing reporting that it didn't. Fixed by extracting the URL as everything between the first `<` and the *last* `>` (not a legal unencoded URI character, so always safe to split on) before ever looking for `rel=` in what follows; `rel`'s own value is now matched tolerant of double-quoted, single-quoted, or bare-token forms via a small, bounded regex (no backtracking risk — every alternative is a simple, non-nested character class).
  - **Rejected, not fixed: a claimed SARIF path-traversal vulnerability.** The review's own two example payloads (`file:///etc/shadow`, a `../../../../` traversal) were traced by hand through `_normalize_sarif_path()` and both were already fully neutralized to safe relative paths before this review — the claim that `normpath` "might leave it intact" didn't match what the code actually does. Not fixed, because there was nothing to fix as described; the real, narrower backslash gap found *while checking* this claim is the sarif.py entry above. **Signing** (`cli/oidc_signer.py`): calls Sigstore's `Signer.sign_dsse()` library API directly (`sigstore.sign.SigningContext` + `sigstore.dsse.Statement`), **not** the `sigstore` CLI. This matters: `sigstore sign` always produces a hashedrekord/`messageSignature` bundle (a signature over raw artifact bytes), never a DSSE envelope, no matter what's passed as input — and `cli/verify.py` calls `Verifier.verify_dsse()`, which requires a real DSSE envelope and rejects a hashedrekord one outright ("cannot perform DSSE verification on a bundle without a DSSE envelope"). `sigstore attest` doesn't fit either: it restricts `--predicate-type` to the SLSA provenance enum and derives its subject from a hash of the predicate file, rather than accepting the already-assembled Statement's own subject (a container image digest). `Signer.sign_dsse()` is the public entry point both CLI subcommands delegate to internally — if you're touching signing, use it directly rather than reintroducing a CLI subprocess. Fetches the ambient OIDC token itself (GitHub Actions `ACTIONS_ID_TOKEN_REQUEST_URL`/`_TOKEN`, or GitLab `CI_JOB_JWT_V2`) and raises rather than silently falling back to an unsigned artifact. The GitHub Actions token fetch retries a transient failure up to `_OIDC_FETCH_MAX_ATTEMPTS` (3) times with a short capped exponential backoff, each attempt bounded by its own `_OIDC_FETCH_TIMEOUT_SECONDS` (10s) timeout — provably bounded (fixed attempts × fixed timeout + capped backoff), never an unbounded/tight retry loop. The full Sigstore bundle (`Bundle.to_json()`) is embedded verbatim in the DSSE envelope under `_sigstore_bundle` — `cli/verify.py` must load it via `Bundle.from_json()` on that embedded bundle, not by hand-reconstructing bundle fields from scraps (an earlier version did this and could never satisfy `sigstore_models`' schema for `tlogEntries`).

**Verification / admission gate** (`cli/verify.py`): rejects any envelope file over `MAX_ENVELOPE_SIZE` (10MB) via a `stat()` size check *before* opening/reading it (`load_envelope()`), so a hostile or corrupt multi-GB file can't exhaust memory just by being pointed at. When `jsonschema` is installed, the predicate is validated against `schema/lucid-attestation-v1.schema.json` before policy/score evaluation and surfaced as `schema_validation_status` — deliberately a `warnings` entry, not a blocking gate: the predicate schema evolves over time (fields get added after real attestations already exist without them), so a mismatch alone must never fail an otherwise-valid run; `jsonschema` missing, the schema file unavailable, or validation itself raising all degrade to `"skipped"` the same way. Mirrors `github_rules.py`'s hardening posture (strict `owner/repo` + hash-shaped-SHA validation before any URL is built, missing-token/401/403/404/transport/malformed-JSON all degrade to `available=False`, never raise) and reuses its `GITHUB_API_BASE`/`DEFAULT_TIMEOUT`/`_REPO_RE`/`_extract_http_error_detail` rather than re-implementing them. Source Level 3 itself still requires no cryptographic commit-signing check (GPG/SSH) — a verified GitHub account is the bar it enforces, per an explicit product decision, not a technical limitation. This module *does* separately extract the commit's `commit.verification` block (`verified`/`reason`, plus a signature-type inferred from the PEM header since GitHub's API exposes no parsed key-ID/fingerprint field) as `commit_signature_verified`/`_reason`/`_type` — a genuinely stronger claim than account-link verification, deliberately kept apart from `verified_github_account` and consumed instead by the Repository & Workstation Governance section below, never by Source Level 3's own semantics. **GitHub-web-flow merge commit walk-back**: GitHub auto-signs *every* merge commit it creates through its own merge API/UI with its own `web-flow` bot key, unconditionally — crediting that as the requested commit's own signature would be a false positive on any push-triggered run after a PR merge (confirmed empirically 2026-09-04: a real GitHub-web merge commit came back `verified: true` via GitHub's key while the PR's actual head commit came back `verified: false, reason: "unsigned"`). `_web_flow_merge_second_parent()`/`_resolve_signature_source()` detect this shape (top-level `committer.login == "web-flow"`, a real unspoofable GitHub user object, plus a >=2-parent merge) and walk back to the merge commit's second parent — the real PR branch tip — evaluating *that* commit's signature instead, bounded to `_MAX_WEB_FLOW_WALK_BACK_HOPS` (5) hops, provably terminating. `commit_signature_source_sha` records which commit the verdict came from (`None` when no walk-back was needed); a failed walk-back reports `commit_signature_verified=None`, never silently crediting the web-flow signature. **Squash/rebase-merge correction (fixed 2026-09-10):** a squash- or rebase-merged commit is also web-flow-signed but has only one parent — nothing for the parent-graph walk-back to reach. Formerly assumed to be a residual gap that "doesn't affect this platform's own repos, which all merge via true 2-parent 'Merge pull request'" — that assumption was wrong: this platform's repos enforce Linear History, which structurally *forbids* a true 2-parent merge, so every real merge here is squash/rebase and this was the *only* case, silently crediting GitHub's own signature on every single PR (confirmed against lucid-assay's real PR #94: squash commit `f931d63...` reported `verified: true` via GitHub's key while the actual human-authored branch tip GitHub squashed, `f8af55a...`, reported `verified: false, reason: "unsigned"`). Closed via `_resolve_squash_or_rebase_source()`: on the first hop, a web-flow-signed commit with no second parent is redirected through `GET /repos/{repo}/commits/{sha}/pulls` (resolve the associated PR) → `GET /repos/{repo}/pulls/{number}/commits` (that PR's own retained commit list, independent of what merging did to `main`) → the last entry is the real pre-squash/pre-rebase branch tip, whose own signature is evaluated instead. Any failure along this path (no associated PR indexed yet — the same race `assay.yml`'s own "Resolve PR Context" step already retries around — transport/shape error, empty commit list) reports `commit_signature_verified=None`, the same fail-closed contract as the 2-parent case; never falls back to crediting the squash/rebase commit's own signature. `verified_github_account`/`name`/`email`/`github_login` are untouched by either walk-back path — a merge commit's own top-level `author` honestly is the human who merged it.

**`_fetch_associated_pr_number()` got the same retry `assay.yml`'s own "Resolve PR Context" step already had, and this module never did, 2026-09-20.** Auditing this platform's own reviewer-confidence gaps (would a PR's own CI signal ever mislead about what happens post-merge) surfaced this asymmetry directly: a PR's own pre-merge run checks its head commit's real signature straight, no walk-back needed at all -- but every one of these repos enforces Linear History, so the *next* run (after merge) always needs the squash/rebase walk-back above, and that walk-back's own first step (`GET /repos/{repo}/commits/{sha}/pulls`, resolving the associated PR) had never actually retried the exact indexing-lag race this same endpoint is already known to hit -- `assay.yml`'s own "Resolve PR Context" YAML step retries 5 attempts/3s apart against a malformed/empty *response body* shape of this race (confirmed for real, 2026-09-03, `lucid-dsse-collector`), but this Python path only ever made one attempt. The equivalent shape here is a well-formed, valid empty JSON array (`[]`) -- which is *also* this function's own honest, legitimate signal for "no PR is associated with this commit at all" (a real, non-error outcome, e.g. an admin-privileged direct push). The two can't be told apart from the response alone, so a genuine indexing lag right after a squash-merge could silently resolve to "no PR" one attempt too early, walking back to nothing and reporting `commit_signature_verified=None` for a commit whose real signature could have been found with one more try.

Fixed with the identical bound the YAML step already uses (`_PR_LOOKUP_RETRY_ATTEMPTS=5`, `_PR_LOOKUP_RETRY_DELAY_SECONDS=3`, provably bounded) -- retries only the "valid empty list" shape, never a genuine transport/HTTP/shape failure (those remain single-attempt, unchanged, since blindly retrying a real 404 isn't what this race is about). A genuinely persistent empty result after all 5 attempts still concludes "no PR" honestly, exactly as before -- this fix reduces false negatives from the race, it doesn't change what a confirmed-empty result means. New tests in `tests/test_commit_author.py`'s `AssociatedPrLookupHelperTests` mock `time.sleep` (same convention `test_verify_hardening.py` already uses for `cli.oidc_signer`'s own retry) and assert: a transient empty-then-real sequence resolves correctly without giving up early; a real transport error is never retried at all; a persistently-empty result after all 5 attempts still returns the same honest "no PR" outcome. `test_no_associated_pr_fails_closed` updated to supply 5 empty responses (previously 1) and assert the full retry count. **`--disallow-degraded` is `reason_code`-aware, not a flat boolean gate.** `RCSResult.degraded_reasons` (`cli/scorer.py`) records *why* a run is degraded -- one entry per independent trigger (`DEGRADED_REASON_*` constants there; branch-governance's and patch-coverage's entries are namespaced `f"branch_governance:{reason_code}"` / `f"patch_coverage:{reason_code}"` when a `reason_code` is set on their respective result objects, else the generic `DEGRADED_REASON_BRANCH_GOVERNANCE_UNVERIFIED` / `DEGRADED_REASON_PATCH_COVERAGE_UNAVAILABLE`) -- and is embedded as `predicate.release_confidence_score.degraded_reasons`. `cli/verify.py`'s `--disallow-degraded` gate only lets a degraded run pass when `degraded_reasons` is non-empty **and every entry** is a member of its `_ALLOWED_DEGRADED_REASONS` set -- currently `"branch_governance:platform_unsupported_tier"` (GitHub Free-plan rulesets limitation) and `"patch_coverage:no_coverable_lines"` (a docs/config-only diff with no code to have coverage over, e.g. a README-only PR). Anything else (a real governance gap, missing PR context, broken SARIF, or `degraded_reasons` missing/malformed on an older or corrupt attestation) still blocks -- fail-closed by construction, not by omission. If you add a new degradation trigger to `score_pipeline()`, give it its own reason code; don't reuse an existing one, or you'll silently change what `--disallow-degraded` exempts. If a trigger is a genuinely unavoidable, non-gameable state (not just "hard to fix"), add its namespaced string to `_ALLOWED_DEGRADED_REASONS` in `cli/verify.py` deliberately -- it isn't automatic. This same fail-closed principle extends to the `degraded` boolean itself, not just `degraded_reasons`: `VerificationResult.degraded` (`cli/verify.py`) is always a concrete bool, never `None` -- an absent field displays as its schema-declared default (`false`, per `schema/lucid-attestation-v1.schema.json`), but `--disallow-degraded` never trusts that display default as a compliance signal. It tracks a separate `degraded_field_present` bool and blocks when the field was missing or malformed, exactly as it would a confirmed `degraded == true` with no exempted reason -- an unconfirmed state must never be treated the same as a confirmed non-degraded one.

Also: on a `pull_request` event, `github.ref_name` resolves to the synthetic `"<number>/merge"` ref, not a real branch — `assay.yml` resolves `--branch` from `github.event.pull_request.base.ref || github.ref_name` instead. If branch governance starts erroring on a nonsense branch name, check that this resolution didn't regress.

relationship between what got scored/attested and what got published). `build` now really builds the image (`docker/build-push-action`), pushing it under its own `ghcr.io/lucid-provenance/lucid-assay-ci-subject:<sha>` package — deliberately not the canonical tag, to avoid two builds racing for one shared tag — and binds `cli.main --image-digest` to whichever real digest that produced: the pushed registry manifest digest in a trusted context (push/workflow_dispatch/same-repo PR), or a local-only image-config digest for a fork PR/Dependabot run (GitHub downgrades that run's `GITHUB_TOKEN` to read-only regardless of the job's own `packages: write`, so nothing is pushed in that case — the image is still really built and loaded locally, never fabricated). `publish` (`needs: [build, attest, verify]`, push-to-main only) then promotes that exact digest to the canonical tag via `docker buildx imagetools create` — a registry-to-registry copy, never a rebuild — before cosign-signing it. `needs: verify` is what makes this a real gate, not just a wiring convenience: `publish` cannot run at all unless `verify`'s own admission checks (`--min-rcs 65`, `--require-slsa-build-l3`, and on push-to-main `--disallow-degraded`) already passed against the real signed envelope — the same "wait for the real CI run to succeed before promoting" discipline `lucid-dsse-collector`'s `deploy-staging.yml` already established (PR #62), done here as an in-run `needs:` edge specifically to avoid ever reaching for `workflow_run` (see the Pipeline Orchestration precedent this platform has already rejected that pattern for elsewhere).

**Packaging: `schema/` needs `__init__.py` + `[tool.setuptools.package-data]`.** `pyproject.toml`'s `[tool.setuptools.packages.find] include = ["schema*"]` looks sufficient but isn't on its own — setuptools silently skips a directory with no `__init__.py`, and even a real package needs an explicit `package-data` entry to bundle a non-`.py` file (the schema JSON). Without both, a plain `pip install .` never installs `schema/` at all, and `cli/verify.py`'s `_SCHEMA_PATH` (`Path(__file__).resolve().parent.parent / "schema" / "*.json"`) silently resolves to a path that doesn't exist — not a crash, `schema_validation_status` degrades to `"skipped"` by design (see the Verification note above), but permanently, with zero schema-drift diagnostic value, for that install path. This never touched any actual integrity/admission-gate check (`schema_validation_status` only ever feeds `warnings`, never `violations`) — a diagnostics gap, not a security one — but fix it at the source (`schema/__init__.py` + `package-data`) if it ever regresses, don't just work around it in one consumer's build step. Verify any change here empirically (a real `pip install .` into a throwaway venv, checked against `cli.verify._SCHEMA_PATH`), not by reading the config and assuming it works — that's exactly how this bug went unnoticed.

**Functional verification tiers (CI vs CD), contract v2, 2026-09-21.** `cli/parsers/functional_adequacy.py` learned to score a journey at the stage it must be proven at. `.lucid/functional-verification.json` gained a `journeys` object form (`{id, name, tier, description}`, `tier` one of `ci`/`cd`/`both`, **required**) alongside the legacy flat `declared_journeys` list, which reads as all-`ci`. `--functional-tier {ci,cd}` (default `ci`) filters the denominator (`ci` = ci+both, `cd` = cd+both); the other tier's journey ids come back as `adequacy.deferred`, so a 100% at one stage can never hide work owed at the other (the same zero-trust stance as the mixed-language mutation cap: unassessed is unverified). Decisions worth not relitigating:
  - **Dedicated flag, not `--functional-env`.** `--functional-env` is a purely descriptive label (`target_env`) and every current caller already passes one (`ci`); overloading it into a filter would conflate a label with semantics.
  - **Legacy output is byte-identical.** `adequacy.tier`/`deferred`/`journeys` are emitted only for a `journeys` contract or a non-default tier (`FunctionalVerificationReport.journeys is None` is the marker). No existing exact-dict test changed, and stored attestations are unaffected; a missing `tier` means `ci`.
  - **Invalid is loud, never repaired.** A present-but-invalid `journeys` (bad/duplicate id, missing/unknown tier, wrong types) is `reason_code: "config_invalid"` (`unavailable`, amber), not `not_configured` — dropping an entry would shrink the denominator, and defaulting a typo'd tier would silently move a journey. An explicitly *empty* `journeys` is `not_configured`, like the empty legacy list. A legacy contract evaluated at `cd` is `not_configured` for that tier, never 100% of zero.
  - **`execution_aborted` is `cd`-only and evidence-based.** At `cd`, expected report files that don't exist (`FileNotFoundError`) mean the live suite never ran to completion → `met: false`, `execution_aborted`; some readable files still get scored but `met` is forced false; an existing-but-unparseable file stays `report_malformed`. `ci` keeps its pre-tier `report_malformed` for a missing report. It exists so a failed or aborted post-deploy run can be *recorded* rather than vanish — a repo whose submit step only runs when every stage passed cannot otherwise show a CD failure at all.
  - **Standalone `functional-adequacy` subcommand** (`cli/functional.py`) exists because a repo's post-deploy job runs after its build statement is already signed and still needs this evaluator, not a reimplementation. It exits `0` whenever it produced a result (`met: false`, `execution_aborted`, `config_invalid` are results to record, not tool failures); `--functional-tier` is required there so it can never silently default to the wrong stage. `--functional-report` is repeatable (a post-deploy suite writes one JUnit file per stage).
  - **Rollout hazard:** a caller passing `--functional-tier` (or the subcommand) before its `ASSAY_CLI_SHA` pin includes this change fails hard on an argparse `unrecognized arguments` — merge, repin, *then* touch that caller's workflow. `schema/lucid-attestation-v1.schema.json`'s `functional_verification`/`adequacy` blocks are `additionalProperties: false`, so the schema change ships in the same PR (the new fields are optional, so old records still validate).

## Supply Chain Integrity & Attestation Invariants

- **Ground Truth Only:** Never hardcode, mock, or synthesize provenance data, SLSA levels, or attestation payloads in production code (`cli/`). All signals, hashes, check results, and metrics must be dynamically extracted and verified from real build inputs, live runtime environments, or parsed artifacts.
- **Fail-Closed Verification:** If metadata is missing, unverified, or tampered with, evaluation checks must evaluate to `false` or non-compliant. Never default to passing states or fabricate fallback signatures.
- **Test Fixture Isolation:** Mocked payloads and synthetic envelopes are strictly confined to `tests/fixtures/` and unit test suites for boundary testing.
- **Zero-Bypass Policy:** Implementations must reflect genuine pipeline states (e.g., actual Git SHAs, ambient OIDC tokens, deterministic lockfile digests, live static analysis results).
